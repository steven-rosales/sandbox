# Rust Basics

## 1. Learning objectives and conceptual map

By the end of this lecture, you should be able to:

1. Read and write Rust syntax fluently, including its type declarations, expressions, functions, control flow, and pattern matching.
2. Explain Rust's ownership system from first principles, and predict when code moves, copies, borrows, or drops a value.
3. Translate TypeScript object types and discriminated unions into Rust structs and enums.
4. Design functions that communicate ownership and mutability through their types.
5. Build and test a complete command-line program with Cargo.
6. Interpret Rust compiler errors and use them to repair incorrect programs.

**The conceptual model**
-> Rust source code: Types, functions, structs, enums, expressions.
-> Type checking: Are operations and data representations valid?
-> Borrow checking: Are ownership, aliasing, and reference lifetimes valid?
-> Compiled executable: Memory management without a tracing garbage collector.

The critical difference from TypeScript is not that Rust has stronger static types. TypeScript can express complex static types too. The difference is that Rust's type system also constrains ownership and access to memory. The compiler reasons about who may access an object, whether an acess amy mutate it, and whether referenced data will still exist.

This allows memory-safe properties to be checked at compile time without relying on a tracing garbage collector for ordinary safe Rust. It does not mean every runtime error or logical bug disappears.

## 3. Language fundamentals: TypeScript to Rust

### 3.1. Variables, immutability, and shadowing

Consider TS:

```ts
const count: number = 3;

let retries: number = 2;
retries = 1;

const label = "agent";
```

and now Rust:

```rs

let count: i32 = 3;

let mut retries: i32 = 2;
retries = 1;

let label: &str = "agent";
```

Rust's `let` is immutable by default. `let mut` permits reassignment or mutation through that binding, subject to the type and borrowing rules.

An important distinction for TS developers: `const` in TS prevents rebinding but does not deeply freeze and object. An immutable Rust binding also prevents ordinary mutation through that binding, but Rust's full guarantees depend on its ownership and reference rules; Rust can still support interior mutability through special types.

Rust has another powerful mechanism: shadowing.

```rs
let raw: &str = "42";
let raw: u32 = raw.parse().expect("integer expected");
```

The second `raw` is a new binding and may have a different type. This supports a declarative transformation pipeline: `input text -> parsed value -> validated valued -> domain object`. Instead of repeatedly mutating the same variable, we can create new immutable bindings for successive representations.

### 3.2. Static types and inference

Rust generally infers local types but requires explicit types in function signatures.

| Concept               | Rust type                         | Interpretation                       |
| :-------------------- | :-------------------------------- | :----------------------------------- |
| Signed integer        | `i8`, `i16`, `i32`, `i64`, `i128` | Fixed-width signed values            |
| Unsigned integer      | `u8`, `u16`, `u32`, `u64`, `u128` | Fixed-width unsigned values          |
| Machine-sized integer | `isize`, `usize`                  | Architecture-dependent width         |
| Floating point        | `f32`, `f64`                      | IEEE-754 floating point              |
| Boolean               | `bool`                            | `true` or `false`                    |
| Unicode scalar        | `char`                            | Not the same as one UTF-16 code unit |
| String slice          | `&str`                            | Borrowed UTF-8 text                  |
| Owned string          | `String`                          | Owned, growable UTF-8 text           |
| Tuple                 | `(i32, bool)`                     | Fixed heterogenous product           |
| Array                 | `[u32; 3]`                        | Fixed-size homogeneous sequence      |
| Unit                  | `()`                              | No meaningful returned value         |

The main distinction from TS's `number` is that Rust has multiple distinct numeric types. Rust does not automatically convert arbitrary numberic types to each other.

```rs
let x: u8 = 10;
let y: u32 = 20;

let z = x + y; // Type error

let z: u32 = u32::from(x) + y;
```

Integer arithmetic also has finite ranges. For example: $0 \le x_{u8} \le 255$.

In normal debug builds, integer overflow is checked and can panic; release builds ordinarily omit these overflow checks. For correctness-sensitive arithmetic, use explicit operations such as `checked_add`, `checked_mul`, or `saturating_add` instead of relying on overflow behavior.

### 3.3. Expression vs statements

Rust is expression oriented, which makes it pleasant for function-style programming.

```rs
fn classify(score: u32) -> &'static str {
    if score >= 80 {
        "high"
    } else {
        "normal"
    }
}
```

The final expression returns the value. Adding a semicolon changes that expression into a statement whose value is `()`.

```rs
fn square(x: i32) -> i32 {
    x * x // Returns i32
}
```

Compare:

```rs
fn broken_square(x: i32) -> i32 {
    x * x; // Evaluates to (), not i32
}
```

The second function does not compile: its declared return type is `i32`, but the body produces unit.

You can also use a block as an expression:

```rs
let capacity: u32 = {
    let base = 4;
    let replicas = 3;
    base * replicas
};
```

This is useful when a calculation needs temporary variables but should expose only its final result.

### 3.4. Functions and control flow

```rs
fn double(value: u32) -> u32 {
    value * 2
}

fn priority(score: u32) -> &'static str {
    match score {
        0 => "none",
        1..=5 => "low",
        6..=10 => "medium",
        _ => "high",
    }
}
```

`match` is an expression, not merely a `switch` statement. Its arms must produce compatible types when the result is used. We will examine this more in Section 5.

Rust provides `if`, `else`, `loop`, `while`, and `for`. Conditions must be Boolean, there is not TS-style implicit truthiness.

```rs
let values: [u32, 3] = [2, 4, 6];
let mut total = 0;

for value in values {
    total += value;
}

assert_eq!(total, 12);
```

`loop` can return a value through `break`:

```rs
let mut counter = 0;

let answer = loop {
    counter += 1;

    if counter == 3 {
        break counter * 2;
    }
};

assert_eq!(answer, 6);
```

A `while` loop evaluates its Boolean condition before each iteration. `for` traverses iterable values. A loop label such as `'outer:` can identify which nested loop a `break 'outer` or `continue 'outer` targets.

### 3.5. Parsing values and handling absence or failure

Chapter 2 introduces two particularly important libraries types: `String` and `Result`.

```rs
let raw = "42";

let parsed: Result<u32, _> = raw.parse();

let value: u32 = match parsed {
    Ok(number) => number,
    Err(_) => 0,
};
```

`Result<T, E>` means an operation either succeeds with `T` or fails with `E`. It is Rust's typed alternative to relying only on thrown exceptions.

`expect("message")` extracts a successful value but panics on failure, so it is useful for examples and cases where failure genuinely cannot be tolerated. Recoverable input errors should normally be handled explicitly.

## 4. Ownership, borrowing, and memory

### 4.1. Why ownership exists

Consider the problem of allocating an object on the heap.

A program needs to answer three questions:

1. Who is responsible for releasing the allocation?
2. Can multiple parts of the program access it simultaneously?
3. Can the allocation disappear while something still references it?

In GC-based languages, memory tracing and reachability generally handle the first and third questions at runtim. The runtime may also allow multiple mutable references to the same object.

Rust instead makes ownership and borrowing part of its static reasoning. The book states three onwership rules:

- Every value has an owner.
- A value has only one owner at a time.
- When its owner goes out of scope, the value is dropped.

These rules form the foundation of Rust's memory management.

### 4.2. Stack, heap, and `String`

A Rust `String` owns its UTF-8 byte buffer. For example:

```rs
let name: String = String::from("hello");
```

The `name` value owns the allocation. The local value has information such as the pointer to the heap (UTF-8 bytes), the length being 5, and capacity being greater than or equal to 5.

When `name` leaves its scope, Rust runs the relevant destruction logic, releasing the string's owned buffer.

A `String` owns its data; `&str` is a borrowed view over UTF-8 text.

| Operation        | Typical cost             | Ownership impact                   |
| :--------------- | :----------------------- | :--------------------------------- |
| Move a `String`  | O(1) descriptor transfer | Owner changes                      |
| Borrow a string  | O(1) reference creation  | Owner unchanged                    |
| Clone a `String` | O(n) bytes copied        | Creates independent owned contents |
| Drop a `String`  | Deallocation cost        | Owned allocation released          |

These are conceptual costs for ordinary string of length n, not precise timings or guaranteed compiler instruction counts.

### 4.3. An interactive ownership simulator

**Key idea**: Rust distinguishes three fundamentally different opeartions that may appear similar in other languages: copying a value, moving ownership, and borrowing a value.

**Move**: The allocation is not duplicated. Assignment transfers ownership, so the old binding may no longer access the moved value.

```rs
let a = String::from("hello");
let b = a;

// a is no longer usable. b owns the string.
println!("{b}"); // Valid
println!("{a}"); // Compile error
```

**Copy**: `u32` implements `Copy`. Both bindings hold indpendently usable values. No heap-bakced `String` allocation has to be duplicated.

```rs
let a: u32 = 42;
let b = a;

println!("{a}"); // Valid
println!("{b}"); // Valid
```

**Borrow**: The reference reads the same underlying text without becoming its owner. The `&String` reference can coerce to `&str`.

```rs
let a = String::from("hello");
let b: &str = &a;

println!("{b}"); // Valid
println!("{a}"); // Valid
```

**Conflict**: The shared borrow remains live until its use in `println!`, so the overlapping exclusive mutable borrow is rejected.

```rs
let mut a = String::from("hello");

let reader = &a;
let writer = &mut a;

println!("{reader} {writer}");
// Compile error
```

### 4.4. Moves versus deep copies

FOr a non-`Copy` value, assignment ordinarily transfers ownership.

```rs
let first = String::from("model");
let second = first;

// first is invalid here
```

For an explicit independent copy of the string contents:

```rs
let first = String::from("model");
let second = first.clone();

assert_eq!(first, second);
```

Why does Rust not silently clone every heap backed value? Because that would convert an apparently cheap assignment into a potentially expensive allocation and memory copy.

For a string containing n bytes, $T_{clone}(n) = \theta (n)$. An ordinary move of its descriptor does not copy those n bytes: $T_{move}(n) = O(1)$.

This is the reason Rust makes deep cloning explicit. Types such as primitive integers, Booleans, `char`, and certain aggregates of `Copy` fields can implement `Copy`. A type that requires destruction of owned resources, such as `String`, cannot be `Copy`.

### 4.5. Ownership crosses function boundaries

Function calls follow ownership rules too.

```rs
fn consume(name: String) {
    println!("{name}");
}

fn inspect(name: &str) {
    println!("{name}");
}

fn main() {
    let name = String::from("agent");

    inspect(&name); // Borrow
    inspect(&name); // Borrow again

    consume(name); // Move ownership

    // name is unavailable now.
}
```

We can express the intended contract directly in the function signature:

| Signature                   | Meaning                                    |
| :-------------------------- | :----------------------------------------- |
| `fn f(x: String)`           | Takes ownership of `x`                     |
| `fn f(x: &str)`             | Reads borrowed text                        |
| `fn f(x: &mut String)`      | May mutate borrowed owned text             |
| `fn f(x: u32)`              | Receives a copied value                    |
| `fn f(x: String) -> String` | Can receive ownership and return ownership |

A good default fo read-only string-processing functions is `&str` rather than `&String`, because `&str` accepts both string literals and borrowed portions of owned string.

This resembles TS's preference for interfaces that expose only what a function needs, but Rust also expresses whether the function takes ownership of its argument.

### 4.6. Shared and mutable borrowing

Rust's core references rule is:

    **_For overlapping live borrows of the same data, there may be multiple shared borrows or one exclusive mutable borrow, but not both_**

The borrow checker also ensures ordinary references remain valid.

```rs
fn append_suffix(text: &mut String) {
    text.push_str("-complete");
}

fn main() {
    let mut text = String::from("task");

    append_suffix(&mut text);

    println!("{text}");
}
```

The `&mut` parameter temporarily grants the function exclusive mutable access. This is not the same as transferring ownership. The caller still owns the string.

**Why exclusivity matters**

Imagine two references to one dynamically sized buffer:

- Reference A read the buffer.
- Reference B causes the buffer to grow.
- Growth may require reallocating the backing memory.
- A may now refer to the old allocation.

Rust rejects the problematic overlap statically in ordinary safe code. The general principle is $\text{Active shared access} \implies \text{No conflicting mutation}$ and
$\text{Active shared access} \implies \text{No conflicting mutation}$
This is a memory-access invariant, not a general guarantee of business-logic correctness.

**Borrows end at their last relevant use**

```rs
let mut text = String::from("agent");

let view = &text;
println!("{view}");

text.push_str("-ready"); // Valid
```

Modern Rust analyzes the useful lifetime of the borrow. `view` is not used after the print, so the mutable operation can occur afterward.

You should reason about when a reference is actually used, not merely the closing braces of the scope in which it was declared.

### 4.7. References cannot outlive their referents

Suppose a function creates a local `String` and tries return a reference to that local allocation. The local owner should be dropped when the function returns, leaving the reference invalid.

Rust rejects this kind of dangling reference. The correct design in this situation is generally:

```rs
fn make_name() -> String {
    String::from("agent");
}
```

The function returns ownership of the string. The caller can keep the value alive for as long as needed.

**Important**: Returning an owned value does not necessarily require an additional allocation or deep copy at the function boundary. Rust can move ownership to the caller.

Rust's compiler tracks reference validity using lifetimes. We are learning the implicit rules now; explicit lifetime annotations are convered more fully in Chapter 10.

### 4.8. Slices: borrowing a part of a value

Slices provide borrowed access to a contiguous portion collection.

For UTF-8 strings:

```rs
let text = String::from("agent-ready");

let first: &str = &text[0..5];
let rest: &str = &text[6..];

assert_eq!(first, "agent");
assert_eq!(rest, "ready");
```

The string slice is conceptually a pointer plus a byte length.

Consider:

```rs
let text = String::from("é");
```

The character `é` occupies two bytes in UTF-8. Attempting `&text[0..1]` panics at runtime because it splits a multibyte character. Rust requires valid UTF-8 boundaries for string slicing. A `char` is a Unicode scalar value, not necessarily a complete user-perceived grapheme cluster.

For ordinary tokenization, prefer string operations that understand UTF-8 boundaries, such as `split_whitespace`.

### 4.9. Memory-safety guarantees vs limitation

Ownership and borrowing provide strong guarantees for ordinary safe Rust, but they do not prove that every program is correct.

| Concern                                | What safe Rust gives you                              |
| :------------------------------------- | :---------------------------------------------------- |
| Use-after-free                         | Prevented for ordinary safe references                |
| Double-free through ownership mistakes | Prevented through ownership rules                     |
| Conflicting mutable aliasing           | Controlled through borrowing and safe abstractions    |
| Dangling references                    | Rejected by lifetime analysis                         |
| Out-of-bound indexing                  | Checked at runtime; may panic                         |
| Integer overflow                       | Requires deliberate handling for portable correctness |
| Logical authorization errors           | Not automatically prevented                           |
| Resource leaks                         | Still Possible                                        |
| Deadlocks                              | Still possible                                        |
| Network and storage consistency        | Not established by ownership alone                    |

Unsafe code and foreign interfaces introduce additional obligations that safe Rust alone cannot enforce.

For agent systems, this distinction is essential: Rust can protect the implementation's memory safety while the application must still enforce who is allowed to execute which tool.

## 5. Data modeling with structs and enums

Rust's structs and enums are especially useful for a TS developer who already prefers tagged unions, immutable values, and explicit domain types.

### 5.1. Structs as nominal records

In TS:

```ts
type Request = {
  actor: string;
  units: number;
  approved: boolean;
};
```

In Rust:

```rs
struct Request {
    actor: String,
    units: u32,
    approved: bool,
}
```

Create one instance:

```rs
let request = Request {
    actor: String::from("alice"),
    units: 3,
    approved: false,
}
```

When the field name and variable name coincide, Rust supports field initialization shorthand:

```rs
fn new_request(actor: String) -> Request {
    Request {
        actor,
        units: 1,
        approved: false,
    }
}
```

Rust also supports struct update syntax:

```rs
let original = Request {
    actor: String::from("alice"),
    units: 3,
    approved: false,
};

let revised = Request {
    approved: true,
    ..original,
};
```

**Important**: This resembles JavaScript object spread, but it does not always copy values.

Here, the string field is moved from `original` into `revised`. As a result, `original` cannot subsequently be used as a complete `Request`, although individually unmoved fields can still be accessed where appropiate.

Struct update syntax follows the same ownership rules as everything else.

### 5.2. Tuple structs and unit-like structs

Rust also allows tuply structs:

```rs
struct TokenBudget(u32);
struct RequestCount(u32);
```

These are different ypes even though both contain `u32`. For example, a function expecting `TokenBudge` cannot accept `RequestCount` by accident.

This is stronger than two ordinary TS aliases:

```rs
type TokenBudget = number;
type RequestCount = number;
```

Those TS aliases are interchangeable unless you add a nominal-like branding technique. Rust also supports unit-like structs:

```rs
struct NoOp;
```

These contain no named fields and are useful as distinct marker types or for attaching behavior through trait implementations.

### 5.3. Methods and associated functions

TypeScript classes may combine data and behavior. Rust separates the struct definition from implementation blocks.

```rs
struct Budget {
    limit: u32,
}

impl Budget {
    fn new(limit: u32) -> Budget {
        Budget { limit }
    }

    fn allows(&self, cost: u32) -> bool {
        cost <= self.limit
    }

    fn increase(&mut self, amount: u32) -> Option<u32> {
        let next = self.limit.checked_add(amount)?;
        self.limit = next;
        Some(next)
    }

    fn into_limit(self) -> u32 {
        self.limit
    }
}
```

The method signatures express distinct operations:

| Method receiver          | Semantics                            |
| :----------------------- | :----------------------------------- |
| `&self`                  | Shared, read-only borrow             |
| `&mut self`              | Exclusive mutable borrow             |
| `self`                   | Takes ownership of the receiver      |
| No `self`, such as `new` | Associated function called with `::` |

The `?` operator above is a small preview of Chapter 9: when `checked_add` returns `None`, it returns `None` from `increase` immediately. Otherwise, it extracts the successful value.

Using these methods:

```rs
let mut budget = Budget::new(10);

assert!(budget.allows(5));
assert_eq!(budget.increase(2), Some(12));
assert_eq!(budget.into_limit(), 12);
```

After `into_limit`, the `budget` binding has been consumed.

This example mutates deliberately. In our main program, the authorization decision itself will be a pure function instead.

### 5.4. Deriving standard functionality

By default, Rust does not assume your own structs should be printable, comparable, clonable, or copyable.

```rs
#[derive(Debug, Clone, PartialEq, Eq)]
struct Agent {
    name: String,
    active: bool,
}
```

The `derive` attribute generates implementations of specific traits.

- `Debug`: enables development-focused `{;?}` formatting.
- `Clone`: permits explicit `.clone()`.
- `PartialEq`: provides equality comparisons.
- `Eq`: indicates equality satisfies the stronger equivalence relationship.
- `Copy`: permits implicit copies, but only when all fields support it and the type does not require destruction.

A struct containing an onwed `String` cannot derive `Copy`.

### 5.5. Enums are algebraic sum types

This is where Rust strongly resembles TS discriminated unions.

In TS:

```ts
type Action =
  { type: "read"; resource: string } | { type: "delete"; resource: string };
```

and in Rust:

```rs
enum Action {
    Read {
        resource: String,
    },
    Delete {
        resource: String,
    }
}
```

Rust enum variants can be unit-like, tuple-like, or struct-like:

```rs
enum AgentEvent {
    Started,
    TokensUsed(u32),
    Failed { code: u16, message: String },
}
```

This models the possible states directly in the type system.

The mathematical interpretation is that a product type combines values, while sum type represents a choice among possibilities.

If a struct has one field of type $A$ and one of type $B$, its possible values from a Cartesian product are $|A \times B| = |A||B|$. An enum with variants carrying types $A$ and $B$ has $|A + B| = |A| + |B|$. For example:

```rs
struct BadResponse {
    succeeded: bool,
    output: Option<String>,
    error: Option<String>,
}
```

This representation permits contradictory states such as success with an error or failure with no error information. A more precise domain model is:

```rs
enum Response {
    Success(String),
    Failure(String),
}
```

Now the response is one variant or the other. A value cannot simultaneously contain both variants. This is an example of **making invalid states unrepresentable**.

### 5.6. Exhaustive pattern matching

```rs
enum Status {
    Pending,
    Running,
    Completed,
    Failed,
}

fn is_terminal(status: Status) -> bool {
    match status {
        Status::Completed | Status::Failed => true,
        Status::Pending | Status::Running => false,
    }
}
```

The match must handle every possible variant. If you add `Cancelled` to `Status`, the compiler will reject this function until its match becomes exhaustive.

A `_` wildcard can match anything not previously handled, but overly broad wildcards can hide future domain stats. For core business and security logic, explicit variants are often preferable.

### 5.7. `Option<T>`, `Result<T, E>`, `if let`, and `let...else`

Rust has no ordinary null value for references. Absence is modeled explicitly.

```rs
let value: Option<u32> = Some(10);
let missing: Option<u32> = None;
```

`Option<T>` is equivalent in spirit to the TS union `T | undefined`, but Rust requires you to account for the variant before treating it as `T`.

`Result<T, E>` expresses success or failure:

```rs
fn parse_units(raw: &str) -> Result<u32, &'static str> {
    match raw.parse::<32>() {
        Ok(value) => Ok(value),
        Err(_) => Err("invalid units"),
    }
}
```

The generic `T` and `E` represents different concrete types. Full generic programming comes later.

For handling one interesting case, `if let` is concise:

```rs
let count = Some(5);

if let Some(value) = count {
    println!("Count: {value}");
}
```

For a successful pattern followed by an early exit, use `let...else`:

```rs
fn read_count(value: Option<u32>) -> u32 {
    let Some(count) = value else {
        return 0;
    };

    count
}
```

The `else` branch must diverge, such as with `return`, `break`, or a panic. The bound value `count` is then available in the following statements.

## 6. Implementation lab - Agent tool-request router

We'll implement a command line router that evaluates proposed AI-agent tool requests against a deterministic policy. The project delibaretly separates:

- **Input parsing**: untrusted text -> typed request.
- **Domain modeling**: structs and enums define legal representations.
- **Autorization**: pure funciton producing a decision.
- **Presentation**: convert a decision into output.
- **I/O**: a small imperative shell around the function core.

It is a simulation: no real tools will be executed. This lets us study the language's mechanics without introducing actual security risks, asynchronous execution, or distributed infrastructure.

### 6.1. Architecture

-> stdin - untrusted text: viewer alic reads docs 3
-> Parser - `&str -> Result<Request, ParseError>`: Syntax checking, numeric conversion, owned domain values
-> Policy - `(&Policy, &Request) -> Decision`: Role authorization, checked arithmetic, budget limit
-> Permit: Cost recorded in decision
-> Deny: Explicit reason
-> stdout - formatted decision

### 6.2. Formal policy

There are three roles and three operations.

| Role     | Read    | Summarize | Delete  |
| :------- | :------ | :-------- | :------ |
| Viewer   | Allowed | Denied    | Denied  |
| Operator | Allowed | Allowed   | Denied  |
| Admin    | Allowed | Allowed   | Allowed |

Each operation has a fixed cost multiplier:

| Operation | Cost per unit |
| :-------- | :------------ |
| Read      | 1             |
| Summarize | 2             |
| Delete    | 3             |

The per-request maximum cost is 10. Let:

- $r$ be the requester's role.
- $a$ be the requested action.
- $u$ be requested units, represented as `u32`.
- $m(a)$ be the action's cost multiplier.
- $L$ be the policy limit.

We allow a request precisely when:

$\text{Permit}(r, a, u, L) = \text{Authorized}(r, a) \land (u > 0) \land Fits_{u32)(u m(a) \le L)$

Otherwise, we deny it.

This is a determinist function of typed inputs. Given identical policy and request values, it returns the same decision.

Notice that we must check arithmetic overflow before comparing costs. Otherwise, overflowing arithmetic could produce an incorrect cost and undermine the budget invariant.

We use small amount of `mod` and `pub` syntax to organize files. Their deeper module-system semantics belong to chapter 7.

- `mode parser;` includes `src/parser.ts` as a module.
- `pub` makes an item accessible form its parent or sibling modules through normal visibility rules.
- `crate::model::Request` refers to a type from a project root.

Create the project. Use the Cargo config:

```toml
# Cargo.toml

[package]
name = "agent_router"
version = "0.1.0"
edition = "2024"

[dependencies]
```
